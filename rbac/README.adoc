= Creating a Kubernetes User with RBAC and Custom Kubeconfig

Based on the step-by-step guide: https://medium.com/@sauravkarki102/creating-a-kubernetes-user-with-rbac-and-custom-kubeconfig-step-by-step-guide-2eb3653c0fe9[Creating a Kubernetes user with RBAC and custom kubeconfig]. A few tweaks were needed to make it work.

== Prerequisites

* Access to a Kubernetes cluster (e.g. control-plane node for `ca.crt` and API server address)
* `kubectl` (or alias `k`) configured with cluster-admin for CSR approval and RBAC setup
* `openssl` and `base64` available locally

== 1. Generate key and CSR

Generate a private key:

[source,bash]
----
openssl genrsa -out max.pem 2048
----

Create a certificate signing request (replace `max` and `ciao` with your user and group):

[source,bash]
----
openssl req -new -key max.pem -out max.csr -subj "/CN=max/O=ciao"
----

Kubernetes expects the CSR in base64. Get the value for the next step:

[source,bash]
----
cat max.csr | base64 | tr -d "\n" && echo
----

== 2. Create and approve CSR in Kubernetes

Set the CSR payload and create the CertificateSigningRequest:

[source,bash]
----
CSR=$(cat max.csr | base64 | tr -d '\n')

k apply -f - <<EOF
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: max
spec:
  request: $CSR
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 31536000
  usages:
  - digital signature
  - key encipherment
  - client auth
EOF
----

List CSRs:

[source,bash]
----
k get csr
----

Approve the CSR (required before the cert is issued):

[source,bash]
----
k certificate approve max
----

== 3. Extract the issued certificate

[source,bash]
----
k get csr max -o jsonpath='{.status.certificate}' | base64 --decode > max.crt
----

== 4. Get values for kubeconfig

Encode cert and key for use in kubeconfig (e.g. `client-certificate-data` and `client-key-data`):

[source,bash]
----
cat max.crt | base64 | tr -d "\n" && echo  # output -> client-certificate-data
cat max.pem | base64 | tr -d "\n" && echo  # output -> client-key-data
----

== 5. Role and RoleBinding

Create a Role in namespace `ciao` (adjust namespace and rules as needed):

----
k create ns ciao
----

[source,bash]
----
k apply -f - <<EOF
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: ciao
  name: max-prod-role
rules:
- apiGroups: [""]
  resources:
  - pods
  - pods/log
  - services
  - secrets
  - configmaps
  - pods/exec
  - pods/attach
  - pods/portforward
  verbs:
  - get
  - watch
  - list
  - create
  - delete
  - update
  - patch
- apiGroups: ["apps"]
  resources:
  - deployments
  verbs:
  - get
  - watch
  - list
  - create
  - delete
  - update
  - patch
- apiGroups: ["cert-manager.io"]
  resources:
  - issuers
  - certificates
  verbs:
  - get
  - watch
  - list
  - create
  - update
  - patch
  - delete
EOF
----

NOTE: `pods/portforward`, `secrets`, and `configmaps` are included in the role above.

Create a RoleBinding for user `max`:

[source,bash]
----
k apply -f - <<EOF
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: max-prod-rolebinding
  namespace: ciao
subjects:
- kind: User
  name: max
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: max-prod-role
  apiGroup: rbac.authorization.k8s.io
EOF
----

Role for Monitoring

[source,bash]
----
k apply -f - <<EOF
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: ciao
  name: max-prod-monitor
rules:
- apiGroups: [""]
  resources:
  - pods
  - pods/log
  - services
  - events
  verbs:
  - get
  - list
  - watch
- apiGroups: ["apps"]
  resources:
  - deployments
  - replicasets
  verbs:
  - get
  - list
  - watch
- apiGroups: ["networking.k8s.io"]
  resources:
  - ingresses
  verbs:
  - get
  - list
  - watch
- apiGroups: ["cert-manager.io"]
  resources:
  - issuers
  - certificates
  verbs:
  - get
  - list
  - watch
- apiGroups: ["metrics.k8s.io"]
  resources:
  - pods
  verbs:
  - get
  - list
EOF
----

Binding the Role for Monitoring to Max

[source,bash]
----
k apply -f - <<EOF
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: max-prod-monitor-binding
  namespace: ciao
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: max-prod-monitor
subjects:
- kind: User
  name: max
  apiGroup: rbac.authorization.k8s.io
EOF
----

== 6. Build custom kubeconfig

Add namespace for user max which is using ciao

Set the API server address:

[source,bash]
----
IP=$(ip a show eth1 |grep inet|grep -v inet6|awk -F " " '{print $2}'|cut -d "/" -f1):6443
k config set-cluster kubernetes \
  --certificate-authority=/etc/kubernetes/pki/ca.crt \
  --embed-certs=true \
  --server=https://$IP \
  --kubeconfig=kubeconfig-max.yml
----

[source,bash]
----
k config set-credentials max \
  --client-certificate=max.crt \
  --client-key=max.pem \
  --embed-certs=true \
  --kubeconfig=kubeconfig-max.yml
----

[source,bash]
----
k config set-context max-context \
  --cluster=kubernetes \
  --namespace=ciao \
  --user=max \
  --kubeconfig=kubeconfig-max.yml
----

NOTE: The context switch is important.

[source,bash]
----
k config --kubeconfig=kubeconfig-max.yml use-context max-context
----

Use the new kubeconfig:

[source,bash]
----
export KUBECONFIG=kubeconfig-max.yml
k get pods -n ciao
----

Or without changing the environment:

[source,bash]
----
k --kubeconfig=kubeconfig-max.yml get pods -n ciao
----

== 7. Optional: shell aliases

Add to your `.bashrc` (or equivalent) for quick switching:

[source,bash]
----
alias kmax='export KUBECONFIG=~/ciaobella/rbac/kubeconfig-max.yml'
alias kadmin='export KUBECONFIG=~/.kube/config'
----

NOTE: These aliases swap the entire KUBECONFIG file. For a cleaner workflow, merge both configs and use `k config use-context` instead. See the Single KUBECONFIG section below.

== 9. Testing Permissions

To verify permissions do:

[source,bash]
----
k auth can-i get pods -n ciao --as=max
k auth can-i get secrets -n ciao --as=max
k auth can-i get configmaps -n ciao --as=max
k auth can-i get issuers.cert-manager.io -n ciao --as=max
k auth can-i port-forward pods -n ciao --as=max
# Should be Forbidden - confirms RBAC is scoped correctly
k --kubeconfig=kubeconfig-max.yml get pod -n default
----

== Single KUBECONFIG

You can merge both kubeconfigs so you can switch contexts without swapping files:

[source,bash]
----
KUBECONFIG=~/.kube/config:~/ciaobella/rbac/kubeconfig-max.yml \
  kubectl config view --flatten > /tmp/merged.yml
mv /tmp/merged.yml ~/.kube/config
----

Then switch contexts with:

[source,bash]
----
k config use-context max-context
k config use-context kubernetes-admin@kubernetes
----

To add manually and harder way but  copy the following into the original config under the contexts section:

----
- context:
    cluster: kubernetes
    namespace: ciao
    user: max
  name: max-context
----

And then add the user at the bottom of the original config file:

----
users:
- name: kubernetes-admin
  user:
    client-certificate-data:
    client-key-data:
- name: max
  user:
    client-certificate-data:
    client-key-data:
----

Make it that it will not delete it 
----
k config set-context --current
----
